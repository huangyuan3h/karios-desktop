## 1. 三个真痛点

### 痛点 1：**换电脑也能正常跑**（portability）

**场景**：Mac 坏了 / 升级换新机 / 临时用借来的电脑 → Karios 应该能**一天内**在新机器上跑起来。

| 当前（本地优先） | 评估 |
|------------------|------|
| 换机操作 | dump PG + 拷 .env + 重装 brew services + 重装 cloudflared + 重启 cron + 改密码 + 改域名 DNS 验证 | **1-3 天**（视熟练度）|
| 失败模式 | cron 装错位置、cloudflared tunnel ID 忘了、域名 DNS TTL 48h、PG schema 没装 alembic 跑到最新版 |
| 实际体感 | "我知道该做但我**不想做**" |

**上云后**：

| 方案 | 换机操作 |
|------|----------|
| Neon | 装 FastAPI + 改 .env → 接 Neon URL = **2 小时** |
| Cloudflare R2 backup | 同上 + 拉 R2 数据 restore = **半天** |
| 全云（Vercel + Neon）| `git clone` + `.env` = **10 分钟** |

**结论**：换电脑是真痛点，**本地优先把它放大了**。

### 痛点 2：**系统长期有生命力**（longevity）

**场景**：3 年后 / 5 年后 / 10 年后 —— Karios 还能跑吗？数据还在吗？维护成本可控吗？

| 维度 | 本地 | 上云 |
|------|------|------|
| **数据寿命** | 依赖 Mac 硬盘寿命 + 你记得备份 + 你能恢复 dump | 云厂商 SLA 99.9%+ 自动多区域 |
| **软件升级** | PG 14 → 17 / Python 3.13 / Node 22 自己搞 | 平台自动滚动升级（小版本）|
| **接班人接手** | "看 README" + 你的口头约定 + ~/.zshrc 别名 | 任何人在新机器跑 `pnpm dev` |
| **Code 漂移** | 你哪天不想维护 = 系统死 | 仓库 + 自动化 = 别人可继续 |
| **人为失误** | `rm -rf`、装错包、改坏 schema | 受限于云厂商 sandbox |
| **Mac 物理失效** | 全失（即使有备份，恢复需要几小时）| 数据在云上 = 0 损失 |

**关键事实**：homelab 架构假设**你永远想维护**——这是个**信仰**，不是**契约**。一旦你**厌倦**或**没空**，系统就死了。

**结论**：长期生命力 = **不依赖单一维护者**。云原生代码（schema 干净、迁移脚本完整、容器化）是这个问题的正确答案——**和"上云 DB"不是一回事**。

### 痛点 3：**远程也能访问**（remote access）

**场景**：你在外面 / 出差 / 4G 网络 —— Karios 能用吗？

| 当前架构 | 评估 |
|----------|------|
| 路径 | iPhone → Cloudflare Edge → Tunnel → 你 Mac 上的 FastAPI → 本地 PG |
| 依赖 | Mac 在线 + 网络通 + CF 账号 + Tunnel 进程 + FastAPI 进程 + PG 进程 |
| 失败模式 1（你 Mac 关机）| **全停** |
| 失败模式 2（你 Mac 网络断）| **全停** |
| 失败模式 3（CF 账号被风控）| 域名访问停 |
| 失败模式 4（4G 钓鱼点无 outbound）| 取决于网络 |
| **任意环节掉，整条链路死** | — |

**对比：上云后**

| 路径 | iPhone → Cloudflare Edge → Vercel/Cloud Run → Neon |
|------|------|
| 依赖 | CF 账号 + 云平台 + Neon |
| 你 Mac 关机 | **0 影响**（服务在云）|
| 你 Mac 网络断 | **0 影响** |
| CF 账号被风控 | 域名停（可迁 Tailscale Funnel）|
| **只有云平台挂才会全停** | 你 Mac 完全不在路径上 |

**结论**：远程访问当前架构 = "Mac 永远在线"假设。**这是脆弱的**。

## 2. 决策（修正版）

### 2.1 核心结论

> **Karios 的"长期生命力"不能依赖单台 Mac + 单人维护**。
>
> 解决路径不是"立刻全上云"——而是**逐步提升 portability + remote access 的兜底**：
>
> 1. **数据独立于 Mac**（Neon 只读副本 / 定时 sync）—— 即使 Mac 全失，数据可恢复
> 2. **代码 container 化**（Docker 一键起）—— 换电脑从"3 天"降到"2 小时"
> 3. **远程访问多层兜底**（Tunnel + Tailscale Funnel + 临时 VM）—— 任意一层挂不影响使用

### 2.2 与 [`db-direction-2026-08.md`](./db-direction-2026-08.md) §4 的关系

我之前的 §4 决策 **保留**——"Postgres 留在本地"，理由：

- DB 不在公网 = homelab 安全姿态
- 5ms vs 100ms 延迟 = API 可用性

**但 §4 是"当前阶段最优"，不是"5 年后最优"**。

新增**演进路径**：

| 阶段 | 触发 | 行动 |
|------|------|------|
| **现在** | 当前 | 本地 PG + Tunnel + 3 副本备份（[`db-direction-2026-08.md`](./db-direction-2026-08.md) §4）|
| **阶段 2（半年内）** | 满足任一：换电脑 ≥1 次 / 想给朋友账号 / 想远程写盘后 crash 后 5 分钟内恢复 | 加 Neon 只读副本分担外部流量（[`db-direction-2026-08.md` §3.6](./db-direction-2026-08.md)）+ Docker 一键起（§12 #7）|
| **阶段 3（1-2 年）** | 满足任一：Mac 退役 / 你不想天天维护 / 想真公开 demo | FastAPI 上 Cloud Run / Vercel Functions + Neon 主库；Tunnel 退化为 fallback |

**关键约束**：每次演进**保留本地 PG 备份 dump**（3 副本策略不变）—— 即使全上云，回退路径仍是 1 天内可执行。

## 4. 反例：什么时候**不**做这些

| 反例 | 不做的理由 |
|------|-----------|
| 我 Mac 还能跑 5 年没坏 | §13 #1-3 都不急，§12 #7 仍建议做（保险）|
| 我没朋友要访问 | §13 #2-3 不需要 |
| 我愿意天天维护 | §13 #3 不需要；但**§12 #7 仍建议**——你挂了时**自己**也要快速恢复 |
| 收益真起来要退休了 | 此时应**全上云**——不是因为方便，是因为**没人在家维护**了 |

## 6. 2026-08-01 review 后优先级修正

**用户原话**："远程部署的部分先优先级下降一些，我们先保证这个系统和 我个人的 ai agent 打通以及 chrome 替代方案吧，暂时云还有一段路。"

**修正结果**：

| 项 | 旧优先级 | 新优先级 | 触发 |
|----|----------|----------|------|
| §13 #1 Neon 只读副本 | 半年内 | **暂缓** | 用户主动降级 |
| §13 #2 Tailscale Funnel fallback | 0.5 天 | **暂缓** | 同上 |
| §13 #3 临时 VM fallback | 0.5 天 | **暂缓** | 同上 |
| §12 #7 Docker 一键起 | 1-2 天 | **保留** | 痛点 1（换电脑）**不依赖云**，仍可独立推进 |
| §14 #1 AI agent 打通 cookbook | — | **🔥 立即做** | 用户提级 |
| §12 #8 ego-lite 调研 | 2-3 天 | **🔥 立即做** | 用户提级（Chrome 替代）|

> **保留痛点真值**：本文档不改结论——3 痛点仍是真的痛点，§3 行动清单仍有效。只是**当前阶段优先级降级**，不代表放弃。
>
> **下次重读**：当用户**显式收回暂缓**时（满足任一）：Tunnel 长期不稳 / 你决定换电脑 / 你要给朋友账号 / 你真要退休了。本文档即触发重读。
